# AI 网络链路优化调研

调研日期：2026-11-17。范围为第一版工作树的静态审计和公开一手资料；本轮没有真实服务请求、性能测量或代码修改。具体用户的慢与卡顿根因尚未证实。

## 已核实的当前行为

| 项目 | 可配置 API | ChatGPT 订阅 |
|---|---|---|
| 接入 | Worker 中 pi-ai、Node fetch | DevKit Responses，Electron 独立 session.fetch |
| 单次时限 | 60 秒，包括等待和接收 | 180 秒，包括响应体 |
| 总预算 | 每文件 3～30 分钟，且限制请求数 | 未接入 API 同等文件总预算 |
| 请求与重试 | 分块串行；SDK 自动重试关闭；格式修正及截断拆分有界 | 分块串行；SDK 自动重试关闭；格式修正有界 |
| 反馈和恢复 | 阶段、耗时、请求次数；同批有效分块复用 | 运行中显示“正在整理”；底层支持 delta，但适配器未上报；未接入分块恢复 |
| 保存 | 通常按预先确认位置保存；失败可重试保存 | 完成后进入待保存区确认 |

代码入口：[API 适配](../../project/src/modules/api/provider.ts)、[分析 Worker](../../project/src/main/analysis-task.ts)、[订阅适配](../../project/src/modules/subscription/adapter.ts)、[DevKit 响应流](../../project/vendor/siwc/src/responses.ts)、[批量控制](../../project/src/main/batch-controller.ts)。订阅在面板加载、检查资料和发送前可能多次获取模型列表；具体耗时占比未测。订阅仍使用较长引用结构；其响应 incomplete 被 DevKit 抛错，不能直接认定截断后拆分已生效。

API 固定 60 秒可能终止正在持续接收的请求，与 P032 症状相符，但当时是否已有字节没有记录；不能断言当次服务端、代理或模型是根因。两条路径均关闭 SDK 自动重试，不能用 SDK 默认重试解释当前等待。

## 方案比较

| 方案 | 价值 | 代价和待验证 |
|---|---|---|
| 保留现有适配并增加统一测量、分阶段时限 | 改动集中，可先识别瓶颈；区分首文本等待、接收停滞和总预算 | 两网络栈仍可能差异；具体时限须以代表样本测量确定 |
| 将 API 也接入 Electron 系统网络通路，并统一任务事件 | 更一致地使用系统代理；有机会复用订阅既有经验 | Worker 与主进程边界、流式背压、取消、域名/重定向保护及兼容服务须验证；不保证更快 |
| 更换 SDK | 可比较协议、维护性和事件能力 | 迁移与兼容成本高；没有证据证明换库能解决当前卡顿 |
| 增加中转服务 | 可集中管理连接和诊断 | 增加部署、隐私、运营和费用；个人本地产品当前无证据需要 |

推荐先采用第一项建立基线，再用隔离实验比较第二项；其余方案保留为证据驱动的备选。Electron 官方说明 Chromium 网络栈支持系统代理，并与 Node fetch 不同；这说明能力差异，不证明当前某次故障由代理导致。[Electron net](https://www.electronjs.org/docs/latest/api/net)

[AI SDK 设置](https://ai-sdk.dev/docs/ai-sdk-core/settings)区分首个有效输出、输出间隔和总时限，可作为设计参照，不能假定现用 pi-ai 已提供同样选项。[OpenAI 延迟指南](https://developers.openai.com/api/docs/guides/latency-optimization)建议分别测量首输出和端到端延迟；[Anthropic 延迟指南](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency)说明流式改善等待感受、输入输出和模型影响耗时。流式不保证总耗时缩短。

[OpenAI Paste Perfect 示例](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt)在 Electron 主进程处理授权和请求，使用模型发现与流式响应，适合作为订阅集成对照；不同版本的 DevKit 能力和许可仍需逐项核实。不得读取其他应用凭据，不能以 API 密钥费用替代订阅而不告知用户。

## 候选优化与测量

- 先记录准备、鉴权/刷新、请求开始、响应头、首个有效文本、最后输出、校验、保存及失败阶段；统计耗时与次数，不记录正文、密钥、令牌或完整请求地址。
- 为首输出、接收空闲、整个请求和文件总预算设置独立策略；保持用户取消优先、迟到结果不发布，并测试兼容服务的空帧和心跳。
- 测试模型列表在账户、权限、模型变化时的缓存失效；比较订阅短引用协议、输出量和质量。有限并发需检查限流、额外费用、顺序及取消，不能默认启用或保证提速。
- 自动重试仅考虑可识别的暂时性错误，设次数、退避及总预算；鉴权、余额或无效请求应明确提示。不得自动切换服务或无限重试。完整结果保存失败只重试保存；检查点须绑定来源、配置和账户。
- 对比短文、长文、重复批次、慢首响应、持续输出超过旧时限、停滞、断流、429、取消、保存失败和重启。使用本地模拟服务先验证，再由用户选择真实服务和样本；对同类模型与输入分别记录首反馈、总耗时、成功率、请求数及内容完整度。
- 同时检查目标覆盖冲突、流中断时不保存残缺结果、跨重启恢复边界和打包版代理行为。无基线前不承诺秒数或提速比例。
